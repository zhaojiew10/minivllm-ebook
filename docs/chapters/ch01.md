# 第 1 章 从自回归生成到推理引擎

语言模型回答一个问题，表面上是一次文本生成，内部却是许多次有依赖关系的计算。模型先根据提示词预测下一个 token，再把这个 token 接回输入，继续预测后续 token。推理引擎的任务，就是在不破坏这种依赖关系的前提下，组织模型计算、请求调度、显存分配和结果返回。

本章先建立这套整体视角，再进入 MinivLLM 的具体模块。文中“官方指南指出”表示 `HowToApproachvLLM_zh.md` 的陈述；“当前源码”表示对本书所依据仓库快照的静态核对。本章没有在本机运行模型或性能实验，因此不把任何推测的文本、时延或吞吐写成运行结果。

## 自回归生成的基本闭环

给定 token 序列 $x_1,\ldots,x_t$，因果语言模型估计条件分布

$$
p(x_{t+1}\mid x_1,\ldots,x_t)=\operatorname{softmax}(z_t/T),
$$

其中 $z_t$ 是最后位置对应的词表 logits，$T$ 是温度。选择概率最大的 token 是贪心解码；按照分布随机选择则是采样。温度会改变分布形状，但它不会改变模型权重，也不会把一次前向传播变成整段文本的一次性预测。

最小生成循环可以概括为：

```python
token_ids = prompt_token_ids
while not should_stop(token_ids):
    logits = model(token_ids)       # 概念伪代码，并非高效实现
    next_token = sample(logits[-1], temperature)
    token_ids.append(next_token)
```

这里的 `logits[-1]` 很关键。自回归训练让位置 $i$ 的表示预测位置 $i+1$，所以给出提示词后，应使用每个序列最后一个有效位置的 logits，而不是把整个批次、整个序列的 logits 直接展平。MinivLLM 的 `ParallelLMHead.forward()` 在 prefill 时通过 `cu_seqlens_q[1:] - 1` 取出各序列的最后位置，正体现了这一点。

采样得到的新 token 会被追加到 `Sequence.token_ids`。只有随后再次经过模型，它才成为预测下一个 token 的上下文。采样本身不会替模型“继续向前看”。

## 因果注意力为什么允许缓存

解码器的每一层都会由隐藏状态计算查询、键和值，即 $Q$、$K$、$V$。注意力用当前查询与可见位置的键计算权重，再对值加权求和。因果掩码禁止位置 $i$ 读取位置 $j>i$ 的信息，因此历史位置的 $K$、$V$ 不会因为未来追加了 token 而被改写。

这带来一个重要结论：处理新 token 时，只需计算它在这一层的 $Q$、$K$、$V$，把新的 $K$、$V$ 保存下来，再让它们与历史缓存共同参与注意力。无需重新计算所有历史 token 的 $K$、$V$。

KV cache 保存的是各层历史 token 的键和值，不是词表 logits，也不是全部中间激活。缓存用显存换取避免重复计算的能力；上下文越长、并发序列越多，缓存管理就越接近系统问题的核心。

## Prefill 与 decode

一次生成通常分为两个阶段。**Prefill（预填充）**处理提示词。一个长度为 $L$ 的新序列会在一次模型调用中计算其多个位置的隐藏状态，建立各层 KV cache，并取最后位置的分布产生第一个补全 token。

**Decode（解码）**处理已经生成的序列。对每条参与当前步的序列，模型输入是最近一个 token，利用已有缓存计算下一个 token。单条序列在一次 decode 中只有一个新 query token，却可能要读取很长的历史缓存。

两个阶段都不能脱离因果约束理解。Prefill 不是“只算最后一个位置”，因为先前位置的层内表示和 KV 仍需建立；decode 也不是“只运行一小部分模型”，因为嵌入、各解码层、归一化、输出投影等仍会执行，只是新 query 数量变为每序列一个。

MinivLLM 在 `Attention.forward()` 中按阶段分流：prefill 调用变长 FlashAttention，decode 调用读取分页缓存的 paged attention。官方指南特别说明，FlashAttention 关注分块计算与 online softmax，PagedAttention 关注 KV cache 的分块存储与间接寻址，二者不是互斥选项；decode kernel 同时采用这两类思想。

## 从连续缓存到分页缓存

若一条序列包含 $T$ 个 token，模型有 $N$ 层、$H_{kv}$ 个 KV 头，每头维度为 $d$，每个元素占 $s$ 字节，那么仅该序列的 KV 元素存储量可写为

$$
M_{KV}=2NT H_{kv}ds.
$$

系数 2 分别对应 $K$ 和 $V$。实际系统还要考虑批次、对齐、临时张量、模型权重以及分配器状态，不能用这个式子代替整卡显存预算。

简单的连续分配要求为每条序列准备连续地址，容易受到长度未知和碎片的影响。分页管理则把缓存池切成固定 token 容量的块，每条序列用 block table 记录逻辑块到物理块的映射。第 $t$ 个逻辑位置可按下面的方式定位：

```python
logical_block = t // block_size
slot_in_block = t % block_size
physical_block = block_table[logical_block]
flat_slot = physical_block * block_size + slot_in_block
```

当前源码的 `BlockManager` 负责块分配、引用计数和块表维护，`ModelRunner` 生成 `slot_mapping` 与 `block_tables`，Triton kernel 再完成缓存写入和读取。这三层职责不同：调度决定“哪些序列可以运行”，块管理决定“缓存放在哪里”，kernel 决定“如何按地址读写”。

## 调度把单请求生成变成推理服务

多条请求同时到达时，逐条跑完再处理下一条会浪费 GPU 的批处理能力。迭代式调度则在每一步重新选择一组序列，使不同请求可以交错推进。新请求进行 prefill，已有请求进行 decode；完成的请求释放块，等待中的请求随后获得机会。

MinivLLM 的 `Sequence` 保存 token、状态、采样参数和 block table。状态分为 `WAITING`、`RUNNING` 和 `FINISHED`。`Scheduler` 同时受最大序列数、每步 token 预算和可用缓存块约束，而不是只按 batch size 排队。

当前 `Scheduler.schedule()` 先尝试从 waiting 队列安排 prefill；只有没有新增 prefill 批次时，才从 running 队列组织 decode。decode 空间不足时会触发抢占，把序列退回等待队列并释放其块。这里的“优先 prefill”是当前实现的行为，不应泛化为所有推理引擎都采用同一策略。

每步采样后，`Scheduler.postprocess()` 追加 token，并检查三类停止条件：EOS、补全 token 数达到 `max_tokens`、提示词与补全的总长度达到 `max_model_length`。因此 `max_tokens` 很大并不保证一定生成那么多 token。

## 一个请求经过哪些组件

MinivLLM 的端到端调用链可以压缩为下面的伪代码；真实初始化还包含分布式进程、权重加载、预热和 KV 池分配。

```python
for prompt in prompts:
    sequence = Sequence(tokenizer.encode(prompt), block_size, sampling_params)
    scheduler.add_sequence(sequence)

while not scheduler.is_finished():
    seqs, is_prefill = scheduler.schedule()
    input_ids = model_runner.prepare_prefill(seqs) if is_prefill \
                else model_runner.prepare_decode(seqs)
    logits = model_runner.run_model(input_ids, is_prefill)
    token_ids = sampler(logits, temperatures)
    scheduler.postprocess(seqs, token_ids)
```

`LLMEngine.step()` 将上述调度、执行与后处理串起来，`generate()` 反复调用它，直到 waiting 和 running 都为空。最后返回一个字典，其中 `text` 是解码后的补全文本，`token_ids` 是对应的补全 token 列表，而不是包含原提示词的完整输入。

性能优化也分布在这条链上。`torch.compile` 面向算子编译与融合，CUDA Graph 面向固定执行序列的捕获和回放。前者不等于自动加速所有小张量，后者也不等于消除 GPU 计算时间。是否启用以及收益多少，必须结合当前配置和独立测量判断。

## 源码定位

- `src/myvllm/engine/llm_engine.py`：`LLMEngine` 的请求入口、`step()`、生成循环与结果整理。
- `src/myvllm/engine/sequence.py`：序列状态、提示词与补全的边界、token 追加。
- `src/myvllm/engine/scheduler.py`：prefill/decode 调度、停止条件、完成后的资源释放。
- `src/myvllm/engine/block_manager.py`：KV 块、块表、引用计数与哈希结构。
- `src/myvllm/engine/model_runner.py`：模型初始化、输入准备、采样和可选 CUDA Graph。
- `src/myvllm/layers/attention.py`：KV 写入、FlashAttention prefill 与 paged decode。
- `src/myvllm/layers/embedding_head.py`：prefill 最后位置选择和词表 logits 计算。

## 阅读实践与检查清单

1. 用三个提示词 token 手算两轮生成：第一轮是 prefill，第二轮输入什么，缓存新增什么，分别使用哪个位置的 logits？
2. 固定层数、KV 头数、头维度和数据类型，比较序列长度翻倍时 KV 存储量的变化；再分析 batch 翻倍的影响。
3. 令 `block_size=4`、`t=6`，写出一个非连续物理块映射下的 `logical_block`、`physical_block` 和 `flat_slot`。
4. 跟踪 `LLMEngine.step()`，标出“调度前已经存在的 token”和“本步采样后追加的 token”，避免把 decode 的输入与输出错开一位。
5. 区分源码事实与性能主张：能确认调用了某个 kernel，不等于已经证明它更快；吞吐比较必须固定模型、输入、输出长度、精度和硬件。

## 小结

自回归生成把长文本拆解为逐 token 的条件预测。Prefill 建立初始上下文，decode 借助 KV cache 逐步延续上下文；分页块表、迭代调度和模型执行共同解决多请求下的显存与吞吐问题。理解 MinivLLM 时，应先抓住“调度序列—准备张量—执行模型—采样—追加并检查停止”的闭环，再研究各 kernel 和图优化，才不会把局部技巧误认为完整系统。
