# 第 12 章 Scheduler：Prefill、Decode 与抢占

![Sequence 生命周期与调度异常路径图。新请求进入 WAITING，满足 KV 块、序列数和 token 预算后经 Prefill 分配块并进入 RUNNING；RUNNING 上方的 Decode 自循环表示每条序列每轮生成一个 token。Sampler 和 postprocess 追加结果后，若 EOS 且未忽略、完成 token 数达到 max_tokens，或总长度达到已设置的 max_model_length，则进入 FINISHED、释放块并移出运行队列，否则保持 RUNNING。红色虚线表示 Decode 跨块需要新块但无空闲块时，调度器抢占 running 队尾序列，释放其块、清空块表并放回 waiting 队首；token_ids 和已生成内容保留，之后重新 Prefill prompt 与全部已生成 token 来重建 KV，再恢复 Decode。](../resources/diagrams/scheduler-state.svg)

*图 12.1　Scheduler 的正常状态迁移、停止条件与抢占恢复。Prefill 和 Decode 是每轮 schedule 的执行阶段；抢占会把状态退回 WAITING 并释放 KV，但不会删除已有 token，因此恢复时需要重新 Prefill 来重建缓存。（SVG 示意图）*

调度器决定每一轮让哪些序列进入模型，也决定内存不足时牺牲谁的 KV Cache。MinivLLM 的 `Scheduler` 采用等待队列优先 Prefill、运行队列逐 token Decode 的策略，并通过块管理器处理容量。当前源码还包含入场容量检查、预算耗尽时保留序列以及无进展保护；这些细节决定了引擎是能够继续推进，还是丢失请求、永久空转。本章按 `schedule()` 的真实分支重建状态转换。

## 源码定位与调度不变量

| 文件 | 关键位置 | 职责 |
|---|---|---|
| `src/myvllm/engine/scheduler.py` | 第 6—99 行 | 入场检查、Prefill/Decode 调度与抢占 |
| 同上 | 第 102—118 行 | 写回采样 token、停止判断与资源释放 |
| `src/myvllm/engine/sequence.py` | 第 8—86 行 | `WAITING/RUNNING/FINISHED` 与 token 账本 |
| `src/myvllm/engine/block_manager.py` | 第 75—160 行 | 分配、容量检查和物理块追加 |
| `src/myvllm/engine/llm_engine.py` | 第 64—112 行 | `schedule → run → postprocess` 执行闭环 |
| `tests/test_scheduler.py` | 全文 | 序列守恒、预算边界和单序列抢占的测试意图；当前测试已失效 |

`tests/test_scheduler.py` 虽有 8 个测试方法，但所有 `Sequence(...)` 构造都没有传当前签名必需的 `block_size`。因此当前套件会先在构造阶段以 `TypeError` 失败，无法执行到调度断言。本章只引用其测试意图，不把它们作为有效回归证据；需先为每个构造补齐与 `make_scheduler` 一致的 `block_size=4`，再运行并判断调度逻辑。

调度器持有两个 `deque`：`waiting` 保存尚未获得本轮 KV 块的序列，`running` 保存已接纳、需要继续生成的序列。构造参数中，`max_num_sequences` 限制一次返回的序列数，`max_num_batched_tokens` 限制一次调度的 token 预算，`max_cached_blocks` 与 `block_size` 交给 `BlockManager`，`eos` 用于后处理。

几个贯穿全章的不变量是：

1. 新请求先进入 `waiting`，成功分配块后才变为 `RUNNING`；
2. 一次 `schedule()` 只返回 Prefill 批次或 Decode 批次，不把二者混在同一个返回值中；
3. Decode 每条入选序列只计一个 token，但这里的“一个”是一次模型推进的预算单位，不是在此刻立刻执行 `append_token`；
4. 被抢占序列变为 `WAITING`，保留 token 历史，释放物理块，之后重新 Prefill；
5. 完成序列变为 `FINISHED`、释放块并从 `running` 删除，不进入另一个完成队列。

`is_finished()` 只检查 `waiting` 和 `running` 是否同时为空。它依赖后处理及时移除完成序列，而不是扫描所有 `Sequence.status`。

## 入场容量检查：尽早拒绝不可能容纳的 Prompt

`add_sequence` 不再无条件入队。它先用物理块总数检查当前序列的逻辑块数：

```python
capacity = len(self.block_manager.blocks)
if sequence.num_blocks > capacity:
    raise ValueError(...)
self.waiting.append(sequence)
```

`num_blocks` 由当前 `len(sequence)` 和 `block_size` 计算，所以这项检查回答的是“初始 Prompt 按当前长度是否可能整体放入 KV Cache”。若不满足，立即抛出 `ValueError`，避免请求永远停留在等待队列。

这项检查不是整个生命周期的资源证明：它没有按 `max_model_length` 预估未来全部生成块，也没有检查 Prompt 是否能放入 `max_num_batched_tokens`。生成过程中的新块需求仍由 Decode 调度处理；超出单轮 token 预算的 Prompt 则可能由后面的无进展保护暴露。

另外，示例配置中的 `max_num_batched_tokens` 是调度器参数；`ModelRunner.warmup_model` 使用的 `max_num_batch_tokens` 是另一个拼写相近的配置键。分析容量或修改配置时不应把二者当成同一个变量。

## schedule 第一阶段：队首 Prefill 优先

每次调用先初始化空 `scheduled_sequences`、`current_scheduled_tokens=0` 和 `preempted=False`，随后从 `waiting` 队首尝试接纳：

```python
seq = self.waiting[0]
if (self.block_manager.can_allocate(seq)
        and len(seq) + current_scheduled_tokens <= self.max_num_batched_tokens):
    seq = self.waiting.popleft()
    self.block_manager.allocate(seq)
    seq.status = SequenceStatus.RUNNING
    self.running.append(seq)
    scheduled_sequences.append(seq)
    current_scheduled_tokens += len(seq)
else:
    break
```

循环还受 `len(scheduled_sequences) < max_num_sequences` 约束。一个批次可以包含多条完整 Prompt，各条按 `len(seq)` 累加预算。只要本次接纳了一条，`schedule()` 就立即返回 `(scheduled_sequences, True)`，不会继续从 `running` 挑选 Decode 序列。

这一实现有三个直接后果：

- **没有分块 Prefill。** 一条 Prompt 必须整体满足剩余 token 预算，不能只处理前一段后留到下一轮。
- **存在队首阻塞。** 若队首因块不足或 token 超预算而无法接纳，循环直接 `break`，不会扫描后方较短请求。
- **Decode 可补位。** 如果没有接纳任何 Prefill，即使 `waiting` 仍非空，也会继续尝试运行队列；若已有 Prefill 入选，则本轮 Decode 让位。

预算使用完整 `len(seq)`，不是假设扣除前缀缓存后的长度。结合第 11 章的限制，当前不能把跨序列 Prefix Caching 当作降低这一预算压力的可用机制。

## schedule 第二阶段：为 Decode 准备物理槽位

只有 Prefill 返回列表为空时，才进入 `while self.running`。循环每次从左侧弹出一条序列，先调用 `block_manager.can_append(seq)`。能够继续时才检查批次预算，随后执行：

```python
self.block_manager.append(seq)
scheduled_sequences.append(seq)
current_scheduled_tokens += 1
```

这里容易出现时序误读：`append(seq)` 是 `BlockManager` 的物理块维护，不是把新采样 token 加入 `Sequence`。上一轮采样得到的 `last_token` 已在账本中，但跨块时可能还没有 KV 槽位；本轮 Decode 前必须补齐映射。模型运行之后，`postprocess` 才把本轮新 token 加入账本。

### 预算耗尽不能丢序列

当前实现先弹出序列，再处理容量和预算。如果 token 数或序列数达到上限，会执行：

```python
self.running.appendleft(seq)
break
```

因此触发上限的当前序列被放回运行队列，尚未处理的右侧后缀也原样保留。若没有这句 `appendleft`，一条从队列弹出的序列会既不入选也不在任何队列中，后续静默消失。`tests/test_scheduler.py` 的 `TestBug2TokenLimitBreak` 正是针对 token 预算和序列数预算两种变体设计的检查；但其当前构造签名不匹配，需先修复才能作为回归证据。

检查顺序也值得注意：源码先询问 `can_append`，通过后才判断预算；不是先看到预算已满就统一退出。阅读抢占轨迹时应保持这一顺序，不能把两种条件交换。

### 返回前恢复运行队列

已入选 Decode 的序列在循环过程中暂时离开 `running`。只要返回列表非空，末尾执行：

```python
self.running.extendleft(reversed(scheduled_sequences))
```

这会把入选序列放回运行队列前端并恢复原顺序，再接上未处理的后缀。例如初始 `[A,B,C]`，预算只允许 A、B，C 被放回后，最终仍为 `[A,B,C]`。同时，A、B 也存在于本次 `scheduled_sequences`，所以后处理可以直接找到并移除其中已完成的序列。

## 抢占：释放队尾或当前序列

当 `can_append(seq)` 返回 `False`，说明当前最后 token 需要新物理块而没有空闲块。此时先将 `preempted=True`，再按右侧是否还有运行序列分两种情况。

### 情况一：右侧还有序列，抢占队尾

```python
self.running.appendleft(seq)
self.preempt(self.running.pop())
```

当前 `seq` 先放回左侧，随后从右侧弹出另一条序列并抢占。被抢占的是**此刻尚未处理的运行队尾**，不是刚发现无法追加的当前序列，也不是已经放入 `scheduled_sequences` 的序列。循环没有在这里 `break`，所以当前序列之后还会再次从左侧取出，重试 `can_append`；若空间仍不足，可能继续抢占右侧序列。

`preempt(victim)` 精确完成三步：

```python
self.block_manager.deallocate(victim)
victim.status = SequenceStatus.WAITING
self.waiting.appendleft(victim)
```

它的 `token_ids`、Prompt 长度和已生成长度保留；`block_table` 与 `num_cached_tokens` 被清空，状态由 `RUNNING` 回到 `WAITING`。没有 `PREEMPTED` 枚举，也没有把 KV 换出到 CPU 的动作。这是**释放并重算**，不是交换到次级存储。

### 情况二：右侧已空，抢占当前序列

若 `self.running` 在弹出当前序列后已经为空，则执行 `self.preempt(seq)` 并 `break`。当前序列释放全部块、回到等待队列。如果此前已有其他序列入选 Decode，它们仍会在末尾恢复并随本次结果返回；“右侧为空”不应误读为整个调用必然没有其他已调度序列。

被抢占序列重新到队首后，下一次调度仍优先尝试 Prefill。由于缓存计数已归零，它会把保留下来的完整 token 历史重新输入模型，重建 KV，再采样后续 token。它自身已释放的块因匹配内容被清空而禁止命中；其他活跃序列的相同前缀块虽仍可能命中，但活跃命中路径会跳过 token，且缺少历史 KV 读取与 RoPE 偏移，同样不正确。因此不能假设旧前缀命中能安全消除这次重算。

### 一个队列轨迹示例

假设运行队列开始时为 `[A,B,C]`，A 因需要新块而无法追加，且没有此前入选序列：

1. A 被从左端弹出，右侧 `[B,C]` 非空；
2. A 被放回左端，队列恢复 `[A,B,C]`；
3. 队尾 C 被抢占，C 释放块、变为 `WAITING` 并放到等待队列左端；
4. 运行队列成为 `[A,B]`，循环继续，A 会重试容量检查；
5. 若 A、B 最终入选，它们按末尾恢复逻辑回到运行队列；若右侧最终为空且 A 仍无法追加，则 A 本身也被抢占。

所以一次 `schedule()` 可能抢占多条序列，不是固定每次只释放一个块或一个请求。

## 空调度与无进展保护

抢占后允许出现 `scheduled_sequences == []`。此时返回 `([], False)` 是合法状态：它表示本次没有模型工作，但已经释放资源、改变队列。`LLMEngine.step` 看到空列表后直接返回空输出和 0 个处理 token，不调用模型，也不调用 `postprocess`；`generate()` 的下一轮再尝试调度。

相反，如果列表为空、没有发生抢占，且 `waiting` 或 `running` 仍非空，说明队列和资源状态完全没有变化。当前源码会主动抛出 `RuntimeError("Scheduler made no progress: ...")`，而不是让 `generate()` 以相同状态无限循环。错误信息还包含等待数、运行数、空闲块数与总块数，便于区分容量问题与引用计数未归零等问题。

两个保护对应不同阶段：

| 保护 | 触发点 | 能发现的问题 |
|---|---|---|
| `add_sequence` 的 `ValueError` | 请求入队前 | 初始 Prompt 所需块数大于物理总块数 |
| `schedule` 的 `RuntimeError` | 调度后无入选、无抢占且仍有请求 | 例如 Prompt 超过单轮 token 预算，或其他导致永久无法推进的状态 |

若两个队列都为空，空调度不会触发异常，因为引擎本来就已经完成。若本次发生抢占且至少改变了一条序列的位置和资源，保护也不会误报；它以 `preempted` 标志区分“有状态变化的空步”和“真正无进展”。

## postprocess：先追加 token，再判断停止

模型返回采样结果后，`postprocess(seqs, token_ids)` 按 `zip` 对齐每条序列与一个 token。每个循环首先 `seq.append_token(token_id)`，然后计算三个停止条件：

```python
stop_due_to_eos = not seq.ignore_eos and token_id == self.eos
stop_due_to_max_tokens = seq.num_completion_tokens >= seq.max_tokens
stop_due_to_max_length = (
    seq.max_model_length is not None
    and seq.num_tokens >= seq.max_model_length
)
```

三者是“或”关系：

- EOS 在 `ignore_eos=False` 时生效；若忽略 EOS，该 token 可以像普通 token 一样追加并继续生成；
- `max_tokens` 统计 completion，不包含 Prompt；
- `max_model_length` 统计 Prompt 加 completion 的总长度，为 `None` 时不启用这一条件。

因为先追加再判断，触发 EOS 或长度上限的那个 token 已计入 completion，源码没有在这里把 EOS 从 `completion_token_ids` 中删除。满足任一条件后，序列状态设为 `FINISHED`，`BlockManager.deallocate` 释放其块，最后 `self.running.remove(seq)` 将其移出调度视野。

`LLMEngine.step` 随后只从本次入选且已完成的序列收集 `(seq_id, completion_token_ids)`。`generate()` 循环直到两个队列均为空，再按 `seq_id` 排序并解码输出。调度器内部用队列决定服务顺序，最终返回顺序则由这段引擎代码决定，两者不是同一概念。

## 实践检查

1. 先修复 `tests/test_scheduler.py` 中所有 `Sequence` 构造缺少必需 `block_size` 的签名不匹配，再在仓库根目录、依赖齐全的环境中运行 `python -m pytest tests/test_scheduler.py -v`。重点阅读 `TestBug1CanAppendFailure` 和 `TestBug2TokenLimitBreak` 的断言；修复前当前 8 项只会先在 `TypeError` 失败，不能把测试命令或未运行的测试意图等同于有效回归结果。
2. 设置三条运行序列和 2 个 Decode token 预算，手工模拟 `schedule()`：前两条入选后，第三条必须因上限被放回，最终运行队列仍保持 `[A,B,C]`，没有任何序列只存在于局部变量中。
3. 设置 A、B 两条运行序列，令 A 首次 `can_append=False`。确认源码把 A 放回左端、抢占右侧 B，而不是把 A 静默丢弃；再区分这与“只有 A 时抢占 A 并 `break`”的状态转换。
4. 对仅有一条运行序列、无法追加且右侧为空的情形模拟抢占：它应释放块、保留 token、状态变为 `WAITING`，本次 Decode 返回空列表；下一次调度应先尝试完整 Prefill，而不是直接恢复原块表。
5. 分别构造“Prompt 块数超过总容量”和“块数能容纳但长度超过 `max_num_batched_tokens`”两个例子。前者应由 `add_sequence` 提前拒绝，后者说明为什么还需要调度时的无进展异常。
6. 检查 `preempted=True` 与空返回的关系，解释为什么 `LLMEngine.step` 可以安全跳过模型调用，以及为什么完全相同的非抢占空步不能让 `generate()` 继续自旋。
7. 用同一序列分别触发 EOS、`max_tokens` 和 `max_model_length`，在纸上核对追加后的 completion 数量；再设置 `ignore_eos=True`，确认只关闭第一个条件，不会关闭另外两个长度限制。
8. 复盘抢占后的成本：旧 `block_table` 和 `num_cached_tokens` 已清空，完整 token 历史将重新 Prefill。不要把第 11 章所述整体不可用的跨序列前缀缓存写成避免这次重算的现成优化；已释放块禁止命中，活跃块命中路径也不正确。

## 小结

当前 Scheduler 每轮先按 FIFO 队首尝试完整 Prefill，未接纳任何等待序列时才安排 Decode。Decode 在模型执行前维护物理块，预算耗尽会把当前序列放回运行队列，容量不足则优先抢占右侧队尾，无路可退时抢占当前序列。抢占是“释放 KV、回到 WAITING、以后完整重算”，不是交换缓存。在仍有请求时，空调度只有发生抢占、状态已经改变才被允许；否则无进展保护会终止潜在死循环。入场块容量检查、序列守恒和三个停止条件共同构成引擎持续推进与正确释放资源的基础。
