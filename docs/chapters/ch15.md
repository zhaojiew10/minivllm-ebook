# 第 15 章 测试、性能评估、局限与扩展路线

一个小型推理引擎是否可信，不取决于模块名称是否接近成熟框架，而取决于调度不变量、内核数值、跨进程协议和端到端结果能否分别复现。本章给出从 CPU 单元测试到 GPU 基准的验证方法，并明确区分本章编写时已经执行的检查与尚未执行的实验。MinivLLM 适合阅读和实验，不应据此描述为生产级推理系统。

## 源码定位与验证层次

本章对应以下材料：

- `tests/test_scheduler.py`：现有调度器测试；
- `tests/scheduler_tests.md`：测试分类与运行命令；
- `benchmark_prefilling.py`：prefill 注意力实现与耗时比较；
- `benchmark_decoding.py`：四种 paged decode 实现、参考结果与 CUDA Event 计时；
- `benchmark_tps.py`：MinivLLM、vLLM、Transformers 的探索性吞吐比较；
- `pyproject.toml`：Python 与依赖约束。

推荐按“纯 Python 状态机 → 单个 GPU 内核 → ModelRunner 数据准备 → 单卡生成 → 多卡协议 → 性能”的顺序排查。前一层失败时，后一层的吞吐数字通常没有解释价值。

## 第一层：先修复调度器测试签名，再运行

现有文件包含 8 个测试方法，其**测试意图**覆盖三类问题：

- token 预算或序列数预算用尽时，序列不能从 running 队列丢失；
- `can_append=False` 触发抢占时，相关序列仍须可追踪；
- 正常 prefill、正常 decode，以及单序列抢占的基本路径。

但这些测试当前均已失效，不能作为有效回归证据。`Sequence.__init__` 要求必需的 `block_size`，而 8 个测试涉及的所有 `Sequence([...])` 构造都没有传该参数；当前套件会先在构造阶段以 `TypeError` 失败，根本到不了 `schedule()` 和断言。需先把每个构造改为显式传入与 `make_scheduler` 一致的 `block_size=4`，再运行测试、保留完整失败栈和测试数量，才能评价原本的调度回归意图。

`block_manager.py` 使用 `xxhash` 和 `numpy`，所以只按旧说明安装 `pytest xxhash` 并不完整。修复上述签名不匹配后，可使用项目环境执行：

```bash
uv sync --group dev
uv run python -m pytest tests/test_scheduler.py -v
uv run python -m pytest tests/test_scheduler.py::TestSchedulerHappyPath -v
```

测试中的 `MagicMock` 会绕过真实块分配，因此即使修复后 8 项通过，也只能证明其断言覆盖的调度逻辑，不能证明 KV cache、prefix cache 或抢占后重算正确。

建议补充以下 CPU 测试，并始终检查“序列守恒”和“块引用守恒”：

1. `block_size` 边界前、边界上、跨边界的 `can_append` 与 `append`；单列 `block_size=1` 用例，修复前它应暴露永不分配新块的确定缺陷；
2. 完成和抢占后 `ref_count` 回到 0，块恰好回到 free 队列一次；
3. 超过整个 KV 容量的提示立即报错，而不是在 generate 中等待；
4. 调度无任何进展时抛出 `RuntimeError`，避免死循环；
5. `Sequence` pickle 往返后访问所有准备函数所需属性，包括 `block_size`；当前代码应在正常 prefill/decode 准备路径复现 `AttributeError`，修复后再将其转为防回归断言；
6. 有 completion 的序列被抢占后，重新 prefill 是否仍保留完整 token 历史；
7. 同一批两条相同 Prompt 且前一序列仍存活时，检查活跃块命中会跳过 token，并证明当前 prefill 的历史 KV 与 RoPE 偏移不满足正确性要求。

## 第二层：GPU 内核先验正确，再计时

`benchmark_decoding.py` 是较完整的示例。它比较 Naive PyTorch、Fast PyTorch、Triton old、Triton new 四种实现，使用打乱的物理块表，并先与 float32 参考结果比较，再计时。

可运行一个较小矩阵：

```bash
uv run python benchmark_decoding.py \
  --batch-sizes 1 8 --seq-lens 128 512 \
  --iters 100 --warmup 10
```

脚本默认容差为 `2e-2`。`correct=NO` 时仍可能继续输出耗时，这种耗时必须丢弃；加速比以字典中的首个实现，即 Naive PyTorch 为基线。遇到可能污染 CUDA context 的越界错误，脚本会终止进程，不能用后续同进程结果继续比较。

计时函数先预热，再同步，使用两个 CUDA Event 包住指定迭代区间，最后除以迭代数。它测量的是该区间内的 GPU 时间，不包含完整 LLMEngine 的分词、调度和 Python 开销。

输入使用随机张量，命令行没有 seed 参数。需要严格复跑同一组数据时，应在独立进程中先固定 `torch.manual_seed`，再调用 `benchmark(...)`，并记录容差与实现版本。固定 seed 不等于跨 GPU、跨 dtype 或跨内核逐位一致。

`benchmark_prefilling.py` 可直接运行：

```bash
uv run python benchmark_prefilling.py
```

它固定测试多个形状，使用 `time.perf_counter` 并在计时区间前后同步。与 decode 脚本不同，它没有系统地把三种输出与高精度参考结果逐一比较，所以运行后应补做 `max_abs_err` 或 `allclose` 检查，再讨论快慢。

Prefill 还应增加有限 mask 专项测试：当前使用 `-1e10` 而非 `-inf`，全 masked 块可能让中间 `p=1` 并暂时累积，后续有限最大值通常经 `alpha` 下溢清除。测试需分别观察中间 `p、l_i、acc` 和最终输出，不能只凭一个最终随机样例断言 masked 项从未贡献。

还要注意两个解释陷阱：超过 Naive Triton 支持范围时的 `SKIPPED` 不是实测 OOM；`analyze_kernel_launches` 把 grid 中 program 数称为 kernel launch 数，而一次 Triton 启动可以包含整个 grid，因此其中由该数量推导的启动开销不能直接作为性能结论。

## 第三层：端到端生成与 API 契约

单卡集成测试至少应断言：

```python
outputs = llm.generate(prompts, sampling_params)
assert set(outputs) == {"text", "token_ids"}
assert len(outputs["text"]) == len(prompts)
assert len(outputs["token_ids"]) == len(prompts)
assert all(isinstance(x, str) for x in outputs["text"])
```

再分别验证 EOS、`max_tokens`、`max_model_length`、`ignore_eos` 和不等长提示。`max_tokens` 只限制 completion，`max_model_length` 包含 prompt；测试预期不能混用。随机采样下不应固定整段文本，除非同时控制所有进程的随机状态与采样实现。

应为 eager 和 CUDA Graph 建立同一测试集，先断言选中的是大于等于 `bs` 的最小捕获图，再覆盖小批借用较大图、连续变换批大小、块表列数变化、stale `slot_mapping` 以及超过最大图容量。多卡测试还应分别验证 Llama 本地头数契约、worker 反序列化字段、初始化失败、worker 异常、共享内存容量、正常退出与重复退出。当前退出路径不是幂等的，不能只测正常生成。

现有仓库没有覆盖 `ModelRunner`、`LLMEngine.generate`、BlockManager 全生命周期、CUDA Graph 或多进程 TP 的正式 pytest 文件。这是测试覆盖现状，而不是对这些功能作出通过或失败的运行结论。

## 性能指标：明确口径与测量区间

吞吐报告至少区分：

- **端到端时延**：从调用 generate 到所有结果可用，包含主机调度；
- **输出吞吐**：`completion_tokens / elapsed_seconds`，明确是否只计生成 token；
- **TTFT**：首个输出 token 可用的时间，需要额外 instrumentation；
- **逐步 decode 时间**：区分 prefill 与 decode，并报告批大小和上下文长度；
- **显存**：区分当前 allocated、峰值 allocated、reserved 与 KV 池理论字节数。

主机计时应使用 `time.perf_counter`，在区间边界执行必要的 `torch.cuda.synchronize()`；CUDA Event 适合设备区间，不应与端到端时延混称。每个配置先预热，再重复多次，报告中位数和离散程度，而不是挑一次最快结果。

`LLMEngine.generate` 的逐步打印包含调度和主机开销，可用于粗看进展；它使用 `time.time`，且 prefill 按完整序列长度计数，不适合替代上述严格口径。

## benchmark_tps：为何不是严格横向结论

`benchmark_tps.py` 中 `WARMUP_STEPS=2`。MinivLLM、vLLM、Transformers 三条路径的生成函数都先各做 **2 次 warmup，再做 1 次正式测量**，不是每路一次预热。它可以用于探索，但当前三路口径并不完全一致：

- MinivLLM 统计 `outputs["token_ids"]` 的 completion 数，vLLM 统计 `RequestOutput` 的 completion 数；
- Transformers 使用 `max_length=256`，统计返回序列总长度，包含输入，且未采用统一的 chat prompt 路径；
- 三个引擎的 max length、显存配置和执行方式不同；
- Transformers 包装函数没有像另外两个包装函数那样显式调用 `cuda_sync()`；
- 每路只有一次正式测量，没有重复区间或误差报告。

因此，不应把脚本输出直接写成“某框架稳定快多少倍”。公平比较应统一模型快照、权重 dtype、提示模板、输入长度、生成 token 定义、采样参数、预热和计时边界，再分别报告 prefill、decode 与端到端结果。本章没有运行该脚本，也不引用其数值。

## 当前局限：按源码事实列账

1. **图路径未闭环**：示例默认 eager；捕获使用 `max_num_seqs`，其他配置使用 `max_num_sequences`；输出缓冲区按 `vocab_size` 分配，却用于承载 `hidden_size` 的模型隐藏状态。
2. **图选择与 padding 均有缺陷**：`self.graphs` 降序插入，重放的 `next` 实际选择最大可容图而非最小图；部分输入、槽位和块表区域没有统一复位，padding 行可能保留 stale 状态，超过最大图也没有回退。
3. **前缀复用不可用**：已释放块因匹配内容被清空而禁止命中；活跃块仍可能命中并跳过 token，但 prefill 不读历史 KV、RoPE 缺少缓存偏移，会产生错误计算。
4. **worker 序列化确定性阻断**：`__setstate__` 未恢复 `block_size`，正常 prefill/decode 数据准备都会访问依赖它的属性并抛出 `AttributeError`；固定端口、共享内存名及无容量、超时和故障恢复则是其他协议限制。
5. **Llama 多卡头数契约错误**：本地 Q/K/V reshape 使用本地头数，构造 `Attention` 却传全局头数，确定性地阻断 `TP>1`。
6. **实际 loader 不支持可靠 TP 分片**：通用 shape mismatch 回退可能按 `min_size` 截断或部分复制并加入 `loaded_params`，加载摘要可能误报，不能把未失败等同于权重正确。
7. **单 token 块边界失效**：`block_size=1` 时模 1 / 模 0 分支永不分配新块，Decode 会复用旧槽位并缺少新块映射。
8. **退出不幂等**：worker 和 `atexit` 路径存在重复清理可能，`join` 无超时。
9. **API 契约不一致**：`generate` 注解为 `list[str]`，实际返回 dict；同步接口没有流式结果。
10. **采样能力有限**：拒绝近零温度，没有 greedy 路径；基准脚本也缺少统一 seed 配置。
11. **显存配置容易误读**：自动计算会覆盖 `max_cached_blocks`，预算基于当前空闲显存，多进程共享 GPU 时需要额外约束。
12. **测试覆盖不均且现有套件失效**：8 个 Scheduler 测试都因 `Sequence` 构造未传 `block_size` 而先 `TypeError`；其他引擎路径缺少正式回归，prefill benchmark 的数值校验也不足。
13. **支持范围有限**：模型名只匹配 Qwen3-0.6B 和 Llama-3.2-1B-Instruct 两种 basename，并非通用模型加载器。

这些问题不妨碍把项目用于学习，但意味着它尚不具备生产系统所需的兼容性、隔离性、可观测性、故障恢复和持续回归保障。

## 扩展路线：先正确性，后性能与服务化

**第一阶段：建立可回归的正确性基线。** 先修复现有 Scheduler 测试的 `Sequence` 构造签名，再统一配置键和 API 类型，修正图缓冲区形状、最小可容图选择与 padding，恢复 worker 的 `block_size`，让 Llama `Attention` 使用本地头数，并禁止 loader 静默截断冒充完整加载。随后让退出幂等并传播 worker 异常，为 BlockManager、ModelRunner、generate 和 TP 通信增加自动化测试。

**第二阶段：完善语义。** 在正确位置偏移和可变长 paged prefill 之上启用前缀复用；增加 greedy、top-k、top-p、随机种子和停止条件；明确多请求、重复调用 generate 与流式输出的契约。

**第三阶段：基于 profile 优化。** 检查 pinned buffer 是否可复用，减少 `.cpu().tolist()` 同步，测量图外 lm head 与采样开销，为未捕获批次提供 eager 回退，并在多卡上比较通信和计算时间。每项优化都保留 eager 或高精度参考结果。

**第四阶段：才讨论服务化。** 若目标升级为长期服务，还需请求准入、队列公平、取消与超时、进程监督、资源隔离、指标日志、安全边界和版本化部署。这些工作不能由单个 CUDA Graph 或一次吞吐测试替代。

## 实践验证清单

完成一轮实验后，交付物至少包含：

1. 环境版本、完整命令、配置和输入输出长度；
2. 单元测试的通过、失败、跳过数量及失败栈；
3. 内核参考实现、容差、最大误差，以及 `correct=NO` 的剔除说明；
4. 预热次数、重复次数、计时区间、同步位置和原始耗时；
5. eager、Graph、单卡、多卡分别标记为已运行或未运行；
6. 异常与退出测试后的进程、共享内存和显存状态；
7. 不根据理论复杂度或单个脚本推断生产可用性。

## 小结

可靠评估应从可复现环境和正确性开始，再进入内核与端到端性能。本章实际完成了静态解析和轻量 `Sequence` 探针，项目 pytest、CUDA 示例、三个基准以及多卡路径均未运行；现有 8 个 Scheduler 测试还因构造签名不匹配而当前失效。现有代码展示了推理引擎的重要组成，但图选择与前缀复用存在设计缺陷，worker 序列化和 Llama TP 存在静态可证阻断，loader 摘要也不能替代数值验证；合理路线是先修复这些问题并建立有效回归，再依据测量优化，最后才评估服务化。
